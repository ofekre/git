עוזר:
הנה הסבר בסיסי על איך `git rebase -i` (interactive rebase) עובד לצורך איחוד commits:

### 1. הפעלת הפקודה
- **`git rebase -i HEAD~N`** — פותח עורך אינטראקטיבי עבור **`N` ה-commits האחרונים**.
- **`git rebase -i --root`** — פותח עורך אינטראקטיבי עבור **כל ה-commits מההתחלה** (שימושי כשרוצים לאחד גם לתוך ה-commit הראשון של הריפו, כי `HEAD~3` מתוך 4 commits יאפשר לך לאחד רק את ה-3 האחרונים וישאיר 2 commits).

### 2. מה מופיע במסך הראשון (ב-`vim`)
תופיע רשימה של ה-commits **מהישן לחדש** (הראשון למעלה, האחרון למטה), כשליד כל אחד כתוב `pick`:
```text
pick abc1234 commit 1
pick def5678 commit 2
pick ghi9012 commit 3
```
- **`pick`** = להשאיר את ה-commit הזה.
- **`squash`** (או בקיצור **`s`**) = לאחד את ה-commit הזה לתוך ה-commit שמעליו.

לכן, משאירים את השורה הראשונה כ-`pick`, ומשנים את השורות שמתחתיה ל-`squash` (או `s`).
לאחר מכן שומרים ויוצאים מ-`vim` (`Esc`, ואז `:wq` + `Enter`).

### 3. מה מופיע במסך השני
מיד אחרי שתשמור, `git` יפתח שוב את `vim` כדי שתבחר/י **הודעת commit אחת משותפת** לכל ה-commits שאוחדו.
אפשר לערוך את הטקסט להודעה אחת נקייה, ואז שוב לשמור ולצאת (`:wq`).

בסיום, אפשר לבדוק עם `git log --oneline` ולראות שכל ה-commits אוחדו!

עוזר:
הנה הסבר בסיסי על קובץ `.gitignore` ואיך כותבים בו כללים:

### מה זה `.gitignore`?
זהו קובץ טקסט רגיל בשם המדויק **`.gitignore`** שיושב בתיקייה הראשית של ה-repository.
כל שורה בקובץ היא תבנית שאומרת ל-Git אילו קבצים ותיקיות **לא לעקוב אחריהם**, כך שלא יופיעו ב-`git status` ולא יתווספו בטעות ב-`git add .`.

### תחביר בסיסי של תבניות ב-`.gitignore`:
- **שם קובץ ספציפי:** `secret.txt` — מתעלם מהקובץ הזה.
- **כוכבית (`*`) לסיומת:** `*.log` או `*.tmp` — מתעלם מכל הקבצים עם הסיומת הזו.
- **תיקייה שלמה (`/` בסוף):** `folder_name/` — מתעלם מהתיקייה הזו ומכל מה שבתוכה.
- **הערה (`#`):** שורה שמתחילה ב-`#` היא הערה ומתעלמים ממנה.

### דגשים חשובים:
1. **`.gitignore` משפיע רק על קבצים שעדיין לא במעקב (untracked):** אם כבר עשית `git add` ו-`git commit` לקובץ בעבר, הוספתו ל-`.gitignore` לא תסיר אותו ממעקב (כדי להסיר רק ממעקב בלי למחוק מהדיסק משתמשים ב-`git rm --cached <file>`).
2. **בדיקה עם `git status`:** לפני שכותבים את ה-`.gitignore`, מריצים `git status` כדי לראות בדיוק אילו קבצים או תיקיות מיותרים נוצרו (למשל תיקיות של ה-IDE או קבצי הרצה/מטמון של Python), ואז מוסיפים את התבניות שלהם ל-`.gitignore`.
3. **איך יוצרים את הקובץ:** אפשר לפתוח ולערוך עם `notepad .gitignore` או `vim .gitignore` (ושומרים). את קובץ ה-`.gitignore` עצמו נהוג לעשות לו `git add .gitignore` ו-`git commit` כדי שיישמר כחלק מהפרויקט.

הנה הסבר בסיסי על פקודת **`git stash`**:

### מה `git stash` עושה?
כשיש לך שינויים בקבצים שעוד לא עשית להם `commit` (והם מפריעים לך לעבור branch או שאתה רוצה לשמור אותם בצד לרגע), `git stash` עובד כמו **"מגירה זמנית"**:

1. **`git stash`**
   שומר את כל השינויים הלא-שמורים (בקבצים שכבר במעקב של Git) במחסנית זמנית בצד, ומחזיר את התיקייה למצב נקי (כמו ב-commit האחרון).
2. **`git checkout -b <branch-name>`**
   יוצר branch חדש ועובר אליו בפקודה אחת (אחרי שהתיקייה נקייה).
3. **`git stash pop`**
   מוציא את השינויים האחרונים מהמגירה, מחזיר אותם לקבצים ב-branch שבו את/ה נמצא/ת עכשיו, ומוחק אותם מהמגירה.

*(פקודות נוספות שקשורות לזה: `git stash list` מציג מה שמור במגירה, ו-`git stash apply` מחזיר את השינויים בלי למחוק אותם מהמגירה).*

### מה זה `git reflog`?
בניגוד ל-`git log` שמראה רק את היסטוריית ה-commits הנוכחית של ה-branch, **`git reflog`** שומר יומן מקומי של **כל תזוזה ש-`HEAD` עשה** (כל commit, reset, checkout וכו').

כשמריצים `git reflog`, כל שורה תיראה בערך כך:
```text
a1b2c3d HEAD@{0}: reset: moving to HEAD~1
e4f5g6h HEAD@{1}: commit: add important.txt
```
- בצד שמאל מופיע ה-**hash** של ה-commit (למשל `e4f5g6h`), ולידו `HEAD@{1}` (המיקום בהיסטוריה לפני הפעולה האחרונה).

כדי להחזיר את ה-branch ואת הקבצים למצב שהיה לפני הטעות, מריצים:
```bash
git reset --hard <hash>
```
(כשמחליפים את `<hash>` במזהה של ה-commit שבו `important.txt` עדיין היה קיים, כפי שראית ב-`git reflog`).

הנה הסבר בסיסי על **Detached HEAD** ועל **`git switch -c`**:

### 1. מה זה `HEAD` ומה זה `Detached HEAD`?
- במצב רגיל, **`HEAD`** (המצביע של "איפה אני נמצא עכשיו") מצביע על **שם של branch** (למשל `main`), וה-branch עצמו מצביע על ה-commit האחרון.
- כשמריצים **`git checkout <commit-hash>`** (קפיצה ישירות ל-commit ספציפי מהעבר ולא ל-branch), `HEAD` מתנתק מה-branch ומצביע **ישירות על ה-commit עצמו** — זה נקרא **Detached HEAD**.
- **למה זה מסוכן?** אם תעשה/י commits חדשים במצב הזה ואז תחזור/תחזרי ל-`main`, ל-commits האלה לא יהיה שום שם של branch שמצביע עליהם (הם יהיו "יתומים" וקשים לאיתור).

### 2. מה עושה `git switch -c recovery-branch`?
הפקודה `git switch -c <branch-name>` (הדגל `-c` הוא קיצור ל-create) **יוצרת branch חדש** בדיוק על ה-commit שבו את/ה נמצא/ת כרגע, ומעבירה אליו את `HEAD`.
כך ה-commit שיצרת במצב Detached HEAD מתחבר ל-branch אמיתי בשם `recovery-branch` ולא הולך לאיבוד!

### 1. חיבור ריפו מקומי לריפו חדש ב-GitHub

הנה הסבר בסיסי על **`git worktree`**:

### מה `git worktree` עושה?
במצב רגיל, תיקיית הפרויקט שלך יכולה להציג רק **branch אחד בכל רגע**. אם את/ה באמצע עבודה מבולגנת על `feature-heavy` וצריך פתאום לתקן באג דחוף על `main`, בדרך כלל צריך לעשות `git stash` או `commit` חלקי כדי לעבור branch.

**`git worktree`** פותר את זה: הוא מאפשר לך לפתוח **branch אחר של אותו ריפו בתיקייה נפרדת במקביל** — שתי התיקיות חולקות את אותה היסטוריית Git, אבל כל אחת נמצאת על branch אחר ובלי להפריע לשנייה.

### הפקודות הבסיסיות:
1. **`git worktree add ../hotfix-folder main`**
   יוצר תיקייה חדשה ליד התיקייה הנוכחית (`../hotfix-folder`) ופותח בתוכה את ה-branch `main`.
   *(בתוך התיקייה החדשה אפשר לערוך ולעשות `git commit` ישירות על `main`, בזמן שהשינויים הלא-גמורים שלך בתיקייה המקורית נשארים untouched)*.
2. **`git worktree list`**
   מציג את רשימת כל תיקיות ה-worktree הפעילות של הריפו.
3. **`git worktree remove ../hotfix-folder`**
   אחרי שסיימת לתקן ולעשות commit בתיקייה הזמנית וחזרת לתיקייה המקורית, הפקודה הזו מוחקת את התיקייה הזמנית ומנקה את הרישום שלה ב-Git.

הנה הסבר בסיסי על **`git worktree`**:

### מה `git worktree` עושה?
במצב רגיל, תיקיית הפרויקט שלך יכולה להציג רק **branch אחד בכל רגע**. אם את/ה באמצע עבודה מבולגנת על `feature-heavy` וצריך פתאום לתקן באג דחוף על `main`, בדרך כלל צריך לעשות `git stash` או `commit` חלקי כדי לעבור branch.

**`git worktree`** פותר את זה: הוא מאפשר לך לפתוח **branch אחר של אותו ריפו בתיקייה נפרדת במקביל** — שתי התיקיות חולקות את אותה היסטוריית Git, אבל כל אחת נמצאת על branch אחר ובלי להפריע לשנייה.

### הפקודות הבסיסיות:
1. **`git worktree add ../hotfix-folder main`**
   יוצר תיקייה חדשה ליד התיקייה הנוכחית (`../hotfix-folder`) ופותח בתוכה את ה-branch `main`.
   *(בתוך התיקייה החדשה אפשר לערוך ולעשות `git commit` ישירות על `main`, בזמן שהשינויים הלא-גמורים שלך בתיקייה המקורית נשארים untouched)*.
2. **`git worktree list`**
   מציג את רשימת כל תיקיות ה-worktree הפעילות של הריפו.
3. **`git worktree remove ../hotfix-folder`**
   אחרי שסיימת לתקן ולעשות commit בתיקייה הזמנית וחזרת לתיקייה המקורית, הפקודה הזו מוחקת את התיקייה הזמנית ומנקה את הרישום שלה ב-Git.

### 2. יצירת branch חדש בשביל ה-Pull Request
כדי שתוכל לפתוח Pull Request מול `main`, צור branch חדש:

```powershell
git checkout -b submission
```

### 3. העתקת כל התרגילים ו-`history.txt`
העתק לתוך תיקיית הריפו של ההגשה את כל 14 התיקיות (`ex1-vim` עד `ex14-restore`) ואת הקובץ `history.txt`.

> **שים לב לנקודה חשובה ב-Git:**
> מאחר שכל תיקיית תרגיל (`ex1-vim` וכו') היא ריפו בפני עצמו עם תיקיית `.git` נסתרת בתוכה, אם תריץ `git add .` כמו שזה — Git יוסיף אותן כתיקיות מקושרות ריקות (`submodule` / `gitlink`) ולא יעלה את הקבצים שבתוכן ל-GitHub.
> - אם ההגשה צריכה להראות את הקבצים עצמם ב-PR — צריך להסיר (או לשנות שם) לתיקיות ה-`.git` הפנימיות לפני `git add`, **או** לארוז ל-`zip` אם רוצים לשמור גם את היסטוריית ה-`.git` של כל תרגיל (כדאי לוודא את זה מול ההנחיות בצ'אט השני).

### 4. Commit ו-Push ל-GitHub
```powershell

git add .

```
